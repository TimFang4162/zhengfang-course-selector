# 选课表达式核心设计

## 目标

- 用稳定的课程/教学班标识描述抢课目标。
- 将动态变化的数据限制在教学班运行态上。
- 抢课任务不依赖用户当时的查询参数或临时筛选条件。
- 后端只需对明确给出的课程集合扫描教学班并尝试选课。

## 基本对象

抢课表达式涉及三层对象：

1. 大类 `categoryId`
2. 课程 `course.id`
3. 教学班 `class.no`

## 唯一性规则

### 课程唯一标识

一门课程由以下组合唯一确定：

```text
categoryId + course.id
```

原因：

- 课程号本身不应假定在全局唯一
- 在当前系统中，用 `categoryId + course.id` 可以稳定定位一门课程

### 教学班唯一标识

一个教学班由以下组合稳定定位：

```text
categoryId + course.id + class.no
```

原因：

- `class.no` 只在同一门课程内部唯一
- `class.no` 在全局不保证唯一
- 因此不能只用 `class.no` 作为全局规则键

## 稳定信息与动态信息

### 稳定信息

以下信息应视为规则系统中的稳定标识：

- `categoryId`
- `course.id`
- `class.no`

这些字段用于：

- 持久化抢课规则
- 生成表达式
- 后端锁定扫描范围

### 动态信息

以下信息会随着选课过程不断变化：

- `selectedCount`
- `capacity`
- `capacityLeft`
- `has_capacity`

它们不用于标识对象，只用于运行时判断当前是否值得尝试抢课。

## 抢课的本质

抢课任务的本质不是"重新找课程"，而是：

1. 先固定一组稳定的目标课程
2. 周期性扫描这些课程下的教学班
3. 找出满足条件且当前有余量的教学班
4. 对这些教学班发起选课请求

因此，系统的核心工作应是：

- 锁定课程集合
- 动态观察教学班容量变化
- 在容量满足时提交选课

## 为什么表达式要以课程为中心

同一个大类在不同查询参数下能看到的课程集合可能不同，例如：

- 不同专业
- 不同筛选条件
- 不同远程查询结果

因此：

- 大类本身不是稳定的课程集合语义
- 抢课任务不能只保存"某个大类"
- 抢课任务应直接保存明确的课程集合

## 规则实体

为了保证任务语义稳定，规则实体只允许：

1. `course`
2. `class`

不允许：

1. `category` 作为独立任务规则实体

大类只能作为前端课程树中的批量操作入口，不能直接进入后端任务模型。

## 表达式结构

表达式中的每个正向条件都应落到具体课程或具体教学班上。

### 课程级条件

用于描述：

- 扫描这门课程下的所有教学班

示例：

```python
course.categoryId == "1" and course.id == "000000X111A107"
```

### 教学班级条件

用于描述：

- 只允许这门课下的某个具体教学班

示例：

```python
course.categoryId == "1" and course.id == "000000X111A107" and class.no == "03"
```

### 不再允许的表达式语义

不再推荐或依赖这种裸大类条件：

```python
course.categoryId == "1"
```

因为它无法独立表达稳定课程集合，仍然依赖外部查询上下文。

## 表达式示例

### 扫描多门课程

```python
(
  (course.categoryId == "1" and course.id == "000000X111A107") or
  (course.categoryId == "1" and course.id == "000000X111A108") or
  (course.categoryId == "1" and course.id == "000000X111A109")
) and has_capacity and not conflicts
```

### 扫描课程并排除某个教学班

```python
(
  (course.categoryId == "1" and course.id == "000000X111A107")
) and not (
  course.categoryId == "1" and course.id == "000000X111A107" and class.no == "03"
) and has_capacity and not conflicts
```

### 只抢某个具体教学班

```python
(
  course.categoryId == "1" and
  course.id == "000000X111A107" and
  class.no == "03"
) and has_capacity and not conflicts
```

## 后端应如何执行

后端拿到任务后，应按以下方式运行：

1. 从规则中提取精确课程集合 `(categoryId, course.id)`
2. 只对这些课程拉取教学班列表
3. 对每个教学班按规则判断是否属于候选
4. 对候选教学班检查运行态条件：
   - `has_capacity`
   - `conflicts`
   - 其他表达式条件
5. 对最终命中的教学班提交选课请求

后端不应：

- 重新根据大类推导课程集合
- 重新依赖用户最初查询时的专业/筛选参数
- 对未进入规则中的课程做扫描

## 设计结论

可以用一句话概括：

> 课程和教学班标识是稳定的，教学班人数和余量是动态的；抢课任务应固定扫描一组稳定课程，再根据动态容量变化决定是否提交选课。

这也是当前选课表达式、批量选择和后端扫描逻辑应遵守的统一原则。
